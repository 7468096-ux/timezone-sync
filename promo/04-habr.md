## Статья

**Заголовок:** Синхронизация между устройствами без аккаунтов: сквозное шифрование на Web Crypto и Cloudflare D1

**Лид:**
У меня есть маленький бесплатный сервис для поиска времени созвона в разных часовых поясах. Пользователи попросили,
чтобы настройка на телефоне и ноутбуке была одинаковой. Делать регистрацию ради этого не хотелось — ни мне хранить
чужие почты, ни пользователям их вводить. Рассказываю, как сделал синхронизацию без аккаунтов, в которой сервер
не может прочитать данные, и где в этой схеме компромиссы.

**1. Исходная точка: всё в URL**

Изначально сервис был полностью статическим. Настройка (имена, города, пояса, рабочие часы) лежит в localStorage,
а «Поделиться» кодирует её в hash ссылки: `#v2.name~city~tz~hours,…`. Часы — 24-битная маска в hex (или 48 бит,
если у кого-то есть получасы), пояс — индекс в таблице популярных зон или IANA-имя. Hash не уходит на сервер,
так что поделиться можно без бэкенда вообще. После открытия hash стирается из адресной строки, чтобы перезагрузка
не откатывала правки.

Подводный камень: индекс пояса в таблице нельзя менять — старые ссылки сломаются. Поэтому таблицу можно только
дополнять в конец.

**2. Синк: ключ вместо аккаунта**

- При включении устройство генерирует случайный 128-битный ключ и показывает его QR-кодом и ссылкой `#sync.<key>`.
- Из ключа выводятся две независимые вещи:
  - `id = SHA-256("tz-sync:id:" + key)` — идентификатор записи на сервере;
  - `encKey = SHA-256("tz-sync:enc:" + key)` — ключ AES-GCM.
- Данные шифруются на устройстве (`crypto.subtle.encrypt`, случайный 12-байтовый IV на каждую запись),
  на сервер уходят только `id`, `iv` и шифротекст.

Почему просто SHA-256 с разными префиксами, а не PBKDF2/HKDF: ключ — 128 бит настоящей случайности, а не пароль,
перебирать его бессмысленно, растягивание ничего не добавляет. Префиксы дают разделение доменов: по `id` нельзя
получить ключ шифрования. (Если бы ключ придумывал человек, это была бы ошибка — тогда нужен медленный KDF.)

```js
async function derive(key) {
  const id  = hex(await crypto.subtle.digest("SHA-256", enc.encode(`tz-sync:id:${key}`)));
  const raw = await crypto.subtle.digest("SHA-256", enc.encode(`tz-sync:enc:${key}`));
  const aes = await crypto.subtle.importKey("raw", raw, "AES-GCM", false, ["encrypt", "decrypt"]);
  return { id, aes };
}
```

**3. Сервер: Cloudflare Worker + D1**

API из трёх строк:

```
GET /v1/s/:id → { iv, data, updatedAt } | 404
PUT /v1/s/:id ← { iv, data, updatedAt } → { updatedAt } | 409, если на сервере копия новее
```

Таблица — `id, iv, data, updated_at, written_at`. Нет эндпоинта со списком записей, нет IP, нет cookies.
Записи удаляются через год после последней записи. Конфликты — last write wins по времени правки на клиенте:
для настроек одного человека на двух его устройствах этого достаточно, CRDT здесь был бы переусложнением.

Клиент отправляет правку через ~1 секунду после изменения, а забирает чужие каждые 20 секунд, пока вкладка видна,
плюс при фокусе и при возвращении сети.

**4. Компромиссы — честно**

- Ключ в ссылке = доступ. Кто получил ссылку, тот видит и меняет данные. В интерфейсе прямо предупреждаю.
- Часы устройств могут расходиться, и LWW по клиентскому времени может «проиграть» свежую правку. На практике
  редко, но это не банковская система.
- Сервер видит метаданные: когда и как часто пишут, примерный размер данных.

**5. Что ещё было интересно**

- Поиск общего окна через полночь и для поясов со сдвигом в полчаса (Индия +5:30 из Европы — каждая клетка часа
  делится на два чужих получаса).
- 10 языков, включая арабский с RTL, где страница зеркалится, а сетка часов остаётся слева направо.
- Сайт и API — один Worker; деплой из GitHub Actions проверяет заголовки безопасности (HSTS, CSP) на живом сайте.

Код открыт (MIT): https://github.com/7468096-ux/timezone-sync, сам сервис — https://timezone-sync.com.co.
Буду рад критике схемы шифрования в комментариях.
